# ADR-005: Формат архитектурных правил для compliance check

**Статус:** принято  
**Дата:** 2025-04

## Контекст

`architecture_compliance_check` сравнивает реальную структуру проекта с заданными правилами.
Нужен формат для описания этих правил: достаточно выразительный для реальных проектов,
но простой для написания вручную и передачи через MCP-аргументы.

Исходная модель `ArchitectureRules` содержала поля `Dependencies []DependencyRule` и
`Constraints []string`, которые не были реализованы в движке.

## Решение

Схема `.architecture.json` с тремя секциями (см. [04-compliance-spec.md](../04-compliance-spec.md)):

```json
{
  "version": "1.0",
  "layers": [...],               // основа: слои + allow_imports_from
  "forbidden_dependencies": [...], // явные запреты
  "constraints": [...]            // текстовые инварианты для LLM
}
```

**Слой** описывает:
- `patterns` — по каким подстрокам пути определяется принадлежность пакета слою
- `allow_imports_from` — какие слои этот слой может импортировать (проверяется статически)

**Разделение статики и LLM:**
- `layers.allow_imports_from` → проверяется движком по реальному графу (детерминированно)
- `forbidden_dependencies` → проверяется движком как явные запреты
- `constraints` → передаётся только в промт LLM (паттерны, которые нельзя выразить графом)

**Источник правил (приоритет):**
1. Аргумент `target_architecture` в вызове инструмента
2. Файл `.architecture.json` в корне анализируемого проекта
3. Дефолтные правила для стандартной Go-структуры

## Обоснование

**Почему `patterns` (подстроки), а не точные пути:**
- Путь включает module prefix (`github.com/org/repo/internal/domain`) — длинный и специфичный
- Подстрока `"internal/domain"` работает для любого модуля без знания его имени

**Почему `allow_imports_from` (белый список), а не запреты:**
- Белый список строже: всё, что не разрешено — запрещено
- Легче читать: "domain не импортирует ничего" → `allow_imports_from: []`
- Соответствует принципу layered architecture: зависимости направлены вниз

**Почему текстовые `constraints` для LLM, а не только граф:**
- Граф импортов не выражает: "все публичные типы должны быть в domain"
- Граф не выражает: "нет глобального состояния"
- LLM видит код и может проверить такие инварианты — это его сильная сторона

**Почему `.architecture.json` в корне проекта:**
- Правила живут вместе с кодом, версионируются в git
- CI может вызвать compliance check без передачи правил в аргументах
- Разработчики видят архитектурные требования рядом с кодом

## Рассмотренные альтернативы

**YAML:** удобнее для ручного редактирования, но требует внешней зависимости для парсинга.  
**Существующая модель `DependencyRule{From, To, Violation bool}`:** семантически неоднозначна
(Violation — это правило или находка?), не поддерживает слоевую модель.  
**Только текстовые constraints:** нельзя проверить статически, LLM может ошибаться.  
**Только граф-based проверки:** не выражает паттерны уровня кода.

## Последствия

- `domain.ArchitectureRules` должна быть обновлена под новую схему
- `CheckCompliance` должен принимать граф импортов и проверять `allow_imports_from` по нему
- Поле `DependencyRule.Violation bool` устарело — удалить
- Файл `.architecture.json` добавляется в каждый проект, использующий compliance check
- Дефолтные правила в `getDefaultRules()` должны соответствовать новой схеме
