# ADR-003: Статический анализ и обнаружение нарушений

**Статус:** принято  
**Дата:** 2025-04

## Контекст

Для построения графа зависимостей и метрик файлов нужно парсить исходный код.
Требования: работает без установки зависимостей проекта, быстро (< 5 с на 500 файлов),
расширяется на новые языки без изменения оркестрирующего кода.

Исходная реализация использовала `go/ast` напрямую в `engine.go`. После введения
multi-language поддержки (ADR-006) Go-специфичный код вынесен в `internal/analyzer/golang/`.

## Решение

### Go-анализатор (`internal/analyzer/golang/analyzer.go`)

Использует стандартную библиотеку `go/ast` + `go/parser`:

- **Граф импортов:** `parser.ParseFile` с `parser.ImportsOnly` — читает только `import`-блок,
  не парсит тела функций. Фильтрация: только импорты с префиксом модуля из `go.mod` (внутрипроектные).
- **Счёт символов:** `parser.ParseFile` с `parser.ParseComments` — подсчитывает экспортируемые
  `FuncDecl` и `TypeSpec`.
- **Тест-файлы:** суффикс `_test.go`; соседний тест-файл — `<name>_test.go` рядом с `<name>.go`.

### Python-анализатор (`internal/analyzer/python/analyzer.go`) — stub

Определяет язык по маркерам (`pyproject.toml`, `setup.py`, `requirements.txt`).
`BuildImportGraph` возвращает пустой граф. Алгоритмы анализа не реализованы.

### TypeScript-анализатор (`internal/analyzer/typescript/analyzer.go`) — stub

Определяет язык по `tsconfig.json`. `BuildImportGraph` возвращает пустой граф.
Алгоритмы анализа не реализованы.

### Языконезависимые алгоритмы (`internal/analyzer/engine.go`)

Работают на `map[string][]string` (рёбра графа) — не зависят от языка:

**Поиск циклов (`findCycles`):**
- DFS с двумя состояниями: `visited` (глобально посещён) и `inStack` (текущий путь DFS)
- Цикл обнаруживается когда DFS встречает узел, уже находящийся в `inStack`

**Уровни слоёв (`computePackageLevels`):**
- Топологический порядок через рекурсивный DFS с мемоизацией
- `level[node] = max(level[dep] + 1 for dep in deps)` где `level[leaf] = 0`
- Циклы обрабатываются через `inStack` (возвращают 0 без зависания)

**Обнаружение нарушений (`findLayerViolations`):**
- Нарушение: пакет уровня N импортирует пакет уровня M > N (нижний слой импортирует верхний)

## Обоснование

**Языконезависимые алгоритмы отделены от языкоспецифичного парсинга:**
- Graph-алгоритмы работают с любым графом зависимостей, не только с Go-импортами
- Новый язык реализует только `BuildImportGraph` (строит рёбра); циклы и violations — бесплатно

**`go/ast` — стандартная библиотека, нет внешних зависимостей:**
- `ImportsOnly` режим на порядок быстрее полного парсинга
- Не требует `go build` — работает без `vendor` и `go.sum`
- Достаточно для построения графа: имена пакетов, не типы и не вызовы функций

**Динамические уровни слоёв (без хардкода имён):**
- Работают для любой структуры проекта без конфига
- Не нарушаются при переименовании пакетов

## Рассмотренные альтернативы

**`go/packages` (с type checking):** требует установленных зависимостей проекта, значительно
медленнее, избыточно для задачи.  
**Grep по `import` строкам:** ненадёжно (multi-line imports, алиасы, строки в коде).  
**Hardcoded layer names:** не переносимо между проектами, ломается при переименовании пакетов.  
**Единый engine.go без разделения по языкам:** не расширяется без правки оркестрирующего кода.

## Последствия

- Go-анализ работает без установки анализируемого проекта или его зависимостей
- Граф содержит только директории-пакеты, не конкретные файлы
- Циклы обнаруживаются на уровне пакетов, не на уровне функций
- При синтаксических ошибках в файле — файл пропускается, анализ продолжается
- Python и TypeScript получают пустой граф → статические нарушения не обнаруживаются,
  но LLM всё равно видит исходный код и может делать выводы
