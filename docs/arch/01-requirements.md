# Requirements

## Контекст продукта

Команды разработки используют AI-ассистентов (Claude Desktop, OpenCode, Cursor) в повседневной
работе. Когда нужно оценить архитектуру проекта или проверить соответствие принятым решениям,
ассистент должен получить структурированный анализ — не просто прочитать файлы, а получить
готовое заключение с оценкой, проблемами и рекомендациями.

Система предоставляет три специализированных инструмента через протокол MCP, которые AI-ассистент
вызывает как обычные функции. Инструменты применимы к проектам на любом поддерживаемом языке
программирования; язык определяется автоматически или задаётся явно.

---

## Функциональные требования

### FR-1 — Архитектурное ревью проекта

Система анализирует проект целиком и возвращает структурированный аудит-отчёт.

**Входные данные:**
- Путь к проекту (обязательный)
- LLM-провайдер и модель (опциональные, есть дефолты)
- Язык ответа: `ru`, `en`, `zh` (опциональный)
- Список путей к файлам для включения в анализ (опциональный; если не задан — авто-обнаружение)
- Язык программирования: `go`, `python`, `typescript` (опциональный; если не задан — авто-определение по маркерным файлам)

**Система обязана:**
- Определить язык программирования проекта автоматически (по маркерным файлам: `go.mod`, `pyproject.toml`, `tsconfig.json`)
- Построить граф импортов только для внутрипроектных зависимостей (не stdlib, не внешние)
- Обнаружить циклические зависимости через DFS
- Определить уровни пакетов динамически (топологический порядок без хардкода)
- Обнаружить нарушения направления зависимостей (низкоуровневый пакет импортирует высокоуровневый)
- Собрать метрики по каждому исходному файлу: строки, экспортируемые функции/типы, наличие тестов
- Включить в промт до 100 000 символов исходного кода (приоритет — переданный список файлов)
- Собрать git-хотспоты: топ-10 файлов по частоте коммитов (при наличии git)
- Передать всё это LLM с тегом языка в markdown-блоках кода и вернуть его оценку без коррекции score движком

**Формат ответа** (`AuditReport`):
```
score: 0–100
summary: текстовая оценка
issues[]: severity, message, location, suggestion
recommendations[]: string
```

**Нарушения, добавляемые движком** (без влияния на score):
- Критические: import cycle
- Высокие: нарушение направления зависимостей между слоями

---

### FR-2 — Проверка архитектурного соответствия

Система сравнивает фактическую структуру проекта с заданными архитектурными правилами.

**Входные данные:**
- Путь к проекту
- Архитектурные правила (`target_architecture`) — JSON-объект по схеме из [04-compliance-spec.md](04-compliance-spec.md)
- LLM-провайдер, модель, язык ответа
- Язык программирования (опциональный; авто-определение если не задан)

**Если `target_architecture` не передан:** система ищет файл `.architecture.json` в `docs/arch/` проекта.  
Если файл не найден — используются дефолтные правила для стандартной структуры проекта.

**Система обязана:**
- Статически проверить: все ли объявленные слои присутствуют в проекте
- Статически проверить: соблюдает ли каждый пакет правило `allow_imports_from` своего слоя
  (сравнение с реальным графом импортов)
- Передать LLM: правила, фактическую структуру, граф импортов, обнаруженные нарушения
- LLM оценивает глубину нарушений, их архитектурный impact, выставляет score

**Статические нарушения** (добавляются движком независимо от LLM):
- Слой объявлен в правилах, но отсутствует в проекте → severity: high
- Пакет из слоя A импортирует пакет из слоя B, а B не в `allow_imports_from` для A → severity: critical

---

### FR-3 — Аудит модуля

Система выполняет детальный анализ отдельного файла или директории (пакета).

**Входные данные:**
- Путь к модулю (файл или директория)
- Путь к проекту (для контекста относительных путей)
- LLM-провайдер, модель, язык ответа
- Язык программирования (опциональный; авто-определение если не задан)

**Система обязана:**
- Прочитать все исходные файлы модуля, исключая тестовые (критерии определяются анализатором языка)
- Передать исходный код LLM с markdown-блоками, помеченными тегом языка
- Передать фокус-лист: SRP, обработка ошибок, DI, тестируемость, сложность
- Вернуть отчёт с оценкой и конкретными находками, привязанными к функциям и типам

---

### FR-4 — Локализация ответов

Все три инструмента возвращают отчёты на выбранном языке. Поддерживаемые языки: `ru`, `en`, `zh`.
Промты, системные роли, метки разделов и рубрики оценки полностью локализованы.
Дефолтный язык настраивается в конфиге сервера.

---

### FR-5 — Поддержка нескольких языков программирования

Система автоматически определяет язык программирования анализируемого проекта и применяет
соответствующий анализатор. Добавление нового языка не требует изменений в оркестрирующем коде.

**Текущие реализации:**
- `go` — полная: граф импортов через `go/ast`, счёт экспортируемых символов, обнаружение тест-файлов
- `python` — stub: скелет реализован, алгоритмы анализа не реализованы
- `typescript` — stub: скелет реализован, алгоритмы анализа не реализованы

**Определение языка:**
1. Явный аргумент `programming_language` в вызове инструмента
2. Авто-определение по маркерным файлам в корне проекта (`go.mod` → go, `tsconfig.json` → typescript, `pyproject.toml` / `setup.py` → python)
3. Фолбэк на Go, если ни один маркер не найден

---

### FR-6 — Транспорт MCP

Сервер поддерживает два режима:
- **HTTP** (`POST /`) — для интеграции с инструментами через HTTP MCP-клиент
- **stdio** — для интеграции с AI-ассистентами (Claude Desktop, OpenCode) через stdin/stdout

Протокол: JSON-RPC 2.0. Методы: `initialize`, `tools/list`, `tools/call`.

---

### FR-7 — Pluggable LLM-провайдеры

Система поддерживает три провайдера:
- `openai` — OpenAI-совместимый API (gpt-4o и другие)
- `anthropic` — Anthropic API (claude-* модели)
- `mock` — детерминированные ответы без сети (для тестирования)

Провайдер и модель задаются глобально в конфиге и могут быть переопределены для каждого вызова.

---

### FR-8 — Персистентность отчётов

При каждом вызове инструмента система сохраняет отчёт в debug-директории:
- `<tool>_<timestamp>.md` — Markdown для чтения человеком
- `<tool>_<timestamp>.json` — структурированный JSON с метаданными

## Нефункциональные требования

### NFR-1 — Время ответа

- Таймаут LLM-запроса: 10 минут (определяется задержкой провайдера, не системой)
- Статический анализ (граф, метрики, snapshot): ≤ 5 секунд для проектов до 500 файлов
- Нет требований к SLA — инструмент используется интерактивно, не в realtime

### NFR-2 — Параллелизм

- Сервер принимает несколько одновременных запросов
- Максимум 3 параллельных LLM-вызова (семафор); остальные ожидают в очереди
- HTTP-запрос отменяет LLM-вызов при разрыве соединения (через `r.Context()`)

### NFR-3 — Безопасность

- Все пути (project_path, module_path) проходят валидацию: запрещены path traversal (`..`)
- API-ключи читаются из переменных окружения, не из аргументов инструмента
- Сервер не выполняет shell-команды произвольного содержания; единственная внешняя команда —
  `git log` с фиксированными аргументами

### NFR-4 — Надёжность

- LLM-запросы: до 3 попыток с экспоненциальным backoff (1s → 2s → 4s)
- Соблюдение `Retry-After` заголовка при 429/503
- Деградация при недоступности LLM: инструмент возвращает ошибку, сервер продолжает работу
- Деградация при недоступности git: `CollectGitHotspots` возвращает пустой список, анализ продолжается

### NFR-5 — Расширяемость

- Добавление нового языка программирования: реализовать `ProjectAnalyzer` интерфейс и зарегистрировать в `registry.go` — никаких изменений в оркестрирующем коде не требуется
- Граф-алгоритмы (поиск циклов, вычисление уровней слоёв) языконезависимы и находятся в `engine.go`
- Анализ не требует установки зависимостей анализируемого проекта

### NFR-6 — Наблюдаемость

- Структурированные логи с префиксами `[MCP]`, `[TOOL]`, `[snapshot]`
- В debug-режиме: логирование первых 200 символов каждого LLM-запроса и ответа
- Предупреждение если промт превышает 200 000 символов
- Сохранение всех отчётов в debug-директории для постмортема
